# Spesa Intelligente — Contesto progetto per Claude Code

## Cos'è
App Flutter + Firebase di gestione budget familiare basata su "cash stuffing digitale": ogni entrata viene distribuita tra buste prima di essere spesa. Modello Free (analisi via regole, no AI) / Premium (AI generativa, scanner scontrino, previsioni).

## Regole obbligatorie — NON derogabili
- Prima di modificare codice, analizza il repository esistente. Non riscrivere da zero.
- Non eliminare funzionalità esistenti senza spiegare perché.
- Per ogni modifica indica: file, problema, soluzione, rischio, test.
- Procedi per piccoli blocchi, verifica la compilazione (`flutter analyze` + build) dopo ogni blocco.
- L'AI passa SEMPRE da Cloud Functions. Mai chiavi API nel client Flutter, mai hardcoded nel codice — solo `functions/.env`.
- Free non fa mai chiamate AI (costo zero). Premium/Trial sì, con limiti verificati **lato server**, non solo in Flutter.
- Le Firestore Rules isolano i dati per utente e per famiglia — mai lettura/scrittura di dati non propri.
- Se una scelta tecnica è incerta, fermati e proponi alternative invece di introdurre una soluzione fragile.
- Ambiente di sviluppo: Ubuntu. Emulatori Firebase locali per lo sviluppo, connessione reale solo in build release (già gestito in `main.dart` con `kDebugMode`).

## Design System
- Colori: verde `#16B98C` (primario), blu `#2563EB`, viola `#8B5CF6`, arancio `#F59E0B`, rosso `#EF4444`, grigio `#64748B`

Schermate allineate: Home, Buste, Spese, Statistiche, Premium, Scanner scontrino, Scanner scontrino famiglia (Block 11), Lista della spesa, AI Chat, Challenge/Sinking Funds, tutte le schermate Famiglia, Nuova entrata, Login (FASE 11), Onboarding demo + wizard di configurazione (vedi "Onboarding avanzato" più sotto).

### Icone custom (sistema centralizzato)

Preparato in vista della nuova Home (non ancora sviluppata — vedi mockup fornito dall'utente, non ancora incorporato nel layout): un sistema di icone proprietario, coerente in tutta l'app, al posto delle `Icons.*` di Material dove esiste un equivalente mappato.

- **Libreria:** `heroicons` (SVG, stile `outline`/`solid` coerente su tutta la libreria). **Non usare `phosphor_flutter`**: era la prima scelta ma è risultata incompatibile con l'SDK Flutter di questo progetto (la sua `PhosphorIconData extends IconData`, e `IconData` è diventata una classe `final` non più estendibile nelle versioni recenti di Flutter — la build web falliva con un errore di compilazione reale, non rilevato da `flutter analyze`). Verificare sempre con una build reale (`flutter build web --release`, l'unico target compilabile in questo ambiente) prima di considerare compatibile una nuova libreria di icone: l'analyzer da solo non basta per questo tipo di incompatibilità.
- **File:** `lib/theme/icon_palette.dart` (colori) + `lib/widgets/app_icons.dart` (enum `CategoryType`/`ActionType`/`NavType`, mapping icona+colore, widget `AppIcon`/`CategoryIcon`/`ActionIcon`/`NavIcon`/`IconBadge`). Uso: `CategoryIcon(type: CategoryType.casa)`, `ActionIcon(type: ActionType.scanner)`. Non chiamare mai `HeroIcons.*`/`Icons.*` direttamente per una categoria/azione già mappata — così cambiare un'icona per tutta l'app significa modificare una riga in `app_icons.dart`, non ogni schermata.
- **Palette icone:** definita in `icon_palette.dart` (`IconPalette`), **diversa da `AppColors`** in `app_theme.dart` — scelta esplicita dell'utente ("applica subito la nuova palette ovunque [nelle icone]"): la nuova palette (primary `#00A58E`, secondary `#008C8C`, accent `#8C8C8C`, estratta dalla futura Home) è già attiva su tutte le icone custom, mentre bottoni/AppBar/card del resto dell'app restano sul tema attuale (`AppColors`, verde `#16B98C` ecc.) finché non verrà sviluppata la nuova Home. È un disallineamento visivo temporaneo **voluto**, non un bug: quando arriverà la nuova Home, se serve allineare anche `AppColors` alla stessa palette, è una modifica centralizzata (i due file di palette), non schermata per schermata.
- **Colori categoria:** una base coerente di ~13 colori (`IconPalette.green/blue/orange/purple/amber/teal/indigo/pink/red/brown/cyan/emerald/gray`) riutilizzata sulle 26 categorie richieste (Casa=verde, Auto=blu, Spesa=arancione, Svago=viola, Scanner=viola, AI=giallo/arancio, Lista spesa=blu, Challenge=verde/acqua, Premium=viola, come da indicazioni dirette; le altre assegnate per coerenza tematica) — non un colore diverso per ognuna.
- **Cablato in tutte le schermate della richiesta originale** (senza toccare il layout della Home né di nessun'altra schermata, solo icone dentro layout esistenti): barra di navigazione inferiore (`NavIcon`, stato normale/selezionato), Home (azioni rapide, AppBar, drawer, alert budget, CTA), Buste (modifica/elimina/nuova), Spese (FAB), Statistiche (badge AI, pulsante analizza), Obiettivi/Challenge (FAB, icona tipo obiettivo risparmio/tetto di spesa, avviso superamento, template 52 settimane), Lista della spesa (pulsante AI, refresh, aggiungi, chiudi), AI Chat (invia, badge, report mensile con frecce su/giù e le 3 righe punto di forza/attenzione/consiglio), Premium (corona, checkmark funzionalità), Famiglia (invita/rimuovi membro/dashboard/nuova spesa/invito), Onboarding (le 4 icone pagina). **Lasciate volutamente Material** solo poche icone universali/decorative senza un equivalente di categoria sensato: `Icons.menu` (hamburger drawer), `Icons.account_balance_wallet` come marchio testata app in Home/Login (non un'icona di categoria). Le icone busta (`Envelope.icon`, emoji tipo `'🏠'`) **non sono state toccate**: sono dati utente esistenti per busta, non icone di categoria dell'interfaccia — cambiarle sarebbe una migrazione dati, non un lavoro di design system. Scanner scontrino (`scan_receipt_screen.dart`) **non toccato** per istruzione esplicita, anche se contiene ancora icone Material.
- **Impostazioni**: non esiste ancora come schermata dedicata nell'app — non c'è nulla da cablare lì finché non verrà creata.
- **Verificato:** `flutter analyze` pulito, build web reale completata con successo dopo ogni fase di cablaggio, e verifica visiva reale (screenshot via emulatore, due giri distinti) su nav bar, azioni rapide/AppBar/drawer Home, Buste (modifica/elimina), Spese (FAB), Statistiche (previsioni + badge AI, con e senza Premium/Trial attivo), Famiglia (dashboard, inviti), Challenge (template 52 settimane, icona tipo obiettivo), AI Chat (invio messaggio, report mensile) — icone nitide, colori corretti per categoria, nessun overflow in nessuna delle schermate toccate.

**FASE 2 — Firestore Rules + sicurezza (completata).** Trovate e corrette 3 falle reali in `firestore.rules`:
1. **Auto-iscrizione a famiglie altrui**: la regola di creazione di `families/{id}/members/{memberId}` accettava anche `request.auth.uid == memberId`, permettendo a chiunque conoscesse un `familyId` di auto-aggiungersi come membro (anche con `role: "owner"`) bypassando l'intero flusso di invito, con accesso pieno a buste/spese/entrate della famiglia. **Corretto**: ora `allow create: if isOwner()` — l'owner che crea la propria famiglia resta coperto perché a quel punto il documento famiglia esiste già con `ownerId` == suo uid.
2. **`isPremium`/contatori d'uso AI scrivibili liberamente dal client** su `users/{uid}`: le Cloud Function leggono questi campi fidandosi ciecamente, ma il client poteva scriverli direttamente senza passare da `verifyPlayPurchase`. **Corretto**: `firestore.rules` ora blocca in scrittura dal client `isPremium`, `trialEnd`, `scontriniUsati`, `richiesteAiUsate`, `analisiAvanzateUsate`, `playProductId`, `playPurchaseToken`, `playSubscriptionExpiry` (scrivibili solo da Cloud Function via Admin SDK). Questo però rompeva `FirestoreService.startTrial()`, che scriveva questi campi direttamente dal client per il trial simulato (unico modo per i beta tester di provare Premium finché Play Billing reale non è configurato) — **spostato in una nuova Cloud Function `startTrial`** (`functions/index.js`, stesso comportamento di prima: 15 giorni, contatori azzerati), richiamata da `firestore_service.dart` via `cloud_functions`. Scelta confermata esplicitamente dall'utente tra le alternative proposte.
3. (minore) `invites/{id}`: il destinatario poteva modificare qualunque campo dell'invito, non solo lo stato. **Corretto**: `allow update` ora richiede `affectedKeys().hasOnly(['status'])`.

Verificato dopo le modifiche: `npm run lint` in `functions/` pulito, sintassi `firestore.rules` valida (avviata con successo nell'emulatore Firestore), `flutter analyze` senza nuovi errori (solo warning preesistenti non collegati, es. `withOpacity` deprecato).

**FASE 4 — Buste + transazioni + distribuzione entrate (completata).**
1. **Operazioni non transazionali** (rischio race condition individuato in FASE 1): corrette tutte le funzioni che leggevano un saldo e poi lo riscrivevano separatamente. Invece di transazioni Firestore vere e proprie, usato un pattern più semplice ed equivalente — `WriteBatch` + `FieldValue.increment()` — che non richiede nemmeno una lettura preventiva del saldo (il delta è già noto lato client) ed è comunque atomico lato server:
   - `FirestoreService.addExpense`: spesa + decremento saldo busta in un unico batch.
   - `FirestoreService.addIncome` e `distributeIncome`: entrata + incremento saldo/i busta/e in un unico batch (`distributeIncome` risulta non richiamata da nessuna schermata — dead code preesistente, lasciata al suo posto e solo resa coerente, non è stata rimossa perché non è nello scope di questa fase).
   - `FirestoreService.addToChallenge`: `FieldValue.increment` diretto, nessuna lettura preventiva.
   - `FamilyService.addFamilyIncome`: stesso pattern batch, più rilevante qui perché più membri scrivono sulle stesse buste condivise. `FamilyService.addFamilyExpense` era già transazionale correttamente (Blocco precedente) e non è stata toccata.
   - **Verificato con un test reale sull'emulatore Firestore** (non solo lint): 20 "spese" da 10€ lanciate in concorrenza sulla stessa busta con il nuovo pattern hanno prodotto il saldo corretto (300/300, tutte e 20 le spese scritte); lo stesso scenario riprodotto con il vecchio pattern leggi-poi-scrivi ha perso 19 decrementi su 20 (saldo finale 490 invece di 300) — la correzione risolve un bug concreto, non solo teorico.
2. **Modifica busta assente** (solo crea/elimina prima): aggiunta `FirestoreService.updateEnvelope` e, in parallelo, `FamilyService.updateFamilyEnvelope`/`deleteFamilyEnvelope` (la busta familiare non aveva né modifica né eliminazione). Il saldo viene spostato della stessa differenza di budget (`budgetDelta = nuovo budget - vecchio budget`) così che "quanto è già stato speso" resti invariato dopo la modifica, invece di apparire come speso/risparmiato solo per effetto della modifica al budget. `NewEnvelopeScreen`/`NewFamilyEnvelopeScreen` ora accettano un parametro opzionale `envelope` che attiva la modalità modifica riusando lo stesso form, invece di duplicare gli schermi. Icona di modifica in `buste_screen.dart`; tap sulla card o icona elimina in `family_dashboard_screen.dart`.
3. **Distribuzione entrate**: già verificata completa in FASE 1 (doppia conferma esplicita, nessun movimento automatico) — nessun intervento necessario oltre alla correzione transazionale del punto 1.

Verificato: `flutter analyze` senza nuovi errori (stessi 33 preesistenti), `updateEnvelopeBalance` (diventata inutilizzata dopo il refactor di `addExpense`/`addIncome`/`distributeIncome` a batch) rimossa perché senza più alcun chiamante.

L'enforcement definitivo è in `acceptFamilyInvite`, ora dentro una **transazione Firestore** che legge sia il documento invito sia il conteggio membri e scrive il nuovo membro solo se sotto al limite — necessario perché più inviti pendenti accettati nello stesso istante potrebbero altrimenti superare insieme il limite prima che il conteggio si aggiorni (stesso tipo di race condition già risolto altrove nel progetto per saldi busta, FASE 4).
- **UI (`family_screen.dart`)**: chi non ha Premium/Trial attivo non vede più il modulo "Crea famiglia" ma una card informativa con bottone "Vai a Premium" (`_createFamilyPremiumNotice`, stesso stile neutro delle altre card informative del progetto) — **gli inviti pendenti restano sempre visibili e accettabili anche per un utente Free**, dato che unirsi con piano Free a una famiglia altrui resta possibile, solo *creare* una famiglia propria è gated. Aggiunta gestione d'errore dove mancava per due nuovi possibili fallimenti introdotti da questo blocco: il tap su "Accetta" invito (poteva fallire silenziosamente se la famiglia è già piena, senza alcun feedback prima d'ora) e la creazione famiglia (mostra il messaggio reale del server in uno SnackBar invece di fallire senza dire nulla).

1. **Vulnerabilità di sicurezza — famiglia**: `firestore.rules`, `families/{familyId}` aveva `allow update: if isOwner()` senza restrizione sui campi — un owner poteva scrivere direttamente `ownerIsPremium`/`ownerTrialEnd` dal client e sbloccarsi l'accesso famiglia gratis, bypassando `createFamily`/`adminSetPremiumStatus`. 2. **Spese ricorrenti erano Free, non Premium** (contraddiceva un requisito esplicito dell'utente): erano liberamente creabili da chiunque, sia lato client (`recurring_expenses_screen.dart`, nessun controllo `hasAiAccess`) sia lato `firestore.rules` (`allow read, write` senza gate). **Fix**: nuova Cloud Function `addRecurringExpense` (verifica `requireActiveAccess` prima di scrivere), `firestore.rules` ora blocca `allow create: if false` sul client (lettura/modifica/eliminazione di una spesa ricorrente già esistente restano dirette, non è "usare" la funzionalità Premium), `FirestoreService.addRecurringExpense` chiama la Cloud Function invece di scrivere Firestore direttamente, FAB "+" in `recurring_expenses_screen.dart` ora reindirizza a `PremiumScreen` se l'utente non ha `hasAiAccess`. **Verificato con un test reale**: Free rifiutato sia dalla Cloud Function sia da un tentativo di scrittura diretta client; Premium riuscito.
3. **`AppUser` non leggeva `subscriptionTier`**: un Premium senza tier "famiglia" vedeva comunque il form "Crea famiglia" in `family_screen.dart` (gated solo su `hasAiAccess` generico) e falliva solo al salvataggio lato server. **Fix**: nuovo `AppUser.hasFamilyTierAccess` (Trial attivo oppure Premium con `subscriptionTier == 'famiglia'`, stessa logica di `requireFamilyTierAccess` lato server), usato ora in `family_screen.dart` al posto di `hasAiAccess` per il gate di creazione — testo della card informativa aggiornato di conseguenza ("richiede il piano Premium Famiglia" invece di "è una funzione Premium" generico).
